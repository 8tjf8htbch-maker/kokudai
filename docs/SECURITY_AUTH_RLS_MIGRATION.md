# 國大練習：Supabase Auth + RLS 移行計画

## 目的

既存の共有データ（`public.app_state`）と練習・戦績・大会・管理者機能を維持しながら、メンバーごとのアカウント認証とデータベース側のアクセス制御を段階的に導入する。

> この文書は移行計画です。現時点では本番のRLSポリシーや認証動作を変更しません。準備・検証が終わる前に既存の匿名アクセスを遮断すると、全員がアプリを使えなくなる可能性があります。

## 現状確認

- フロントエンドは公開可能な Supabase publishable key を使っている。これは秘密鍵ではないため、ブラウザに置く前提のキーである。
- `app_state` は `anon` と `authenticated` に SELECT を許可するポリシーがある。
- `save_app_state(bigint, jsonb)` は SECURITY DEFINER 関数で、現在は `anon` と `authenticated` の両方に EXECUTE が許可されている。
- 現在の管理者ログインは独自の `admin_accounts` / RPC とブラウザの sessionStorage を利用している。これは Supabase Auth のユーザーセッションと同じものではなく、データベース側で一般メンバーと管理者を安全に区別する仕組みとしては不十分。
- クライアントは `app_state` の行を読み、`save_app_state` RPC で共有状態全体を書き戻す。Realtime の更新も利用する。
- 自動バックアップ workflow は publishable key で `app_state` を REST 読み取りする。RLS変更後もバックアップを継続させる方法を移行前に用意する必要がある。
- GitHub Pages の静的フロントエンドなので、サーバー専用の秘密鍵をフロントエンドに置いてはならない。

## 移行方針

### フェーズ0 — 事前保全と棚卸し（本番設定を変更しない）

1. Supabase の現在の `app_state` を JSON でエクスポートし、暗号化された保管先に保存する。
2. Supabase SQL Editor でテーブル、RLSポリシー、関数の定義と EXECUTE 権限を確認し、現状のスナップショットを安全に保管する。
3. GitHub Actions の「國大練習 バックアップ・稼働維持」を手動実行し、keepalive とバックアップの両方が成功することを確認する。
4. 現在の管理者アカウントを使って、練習作成、結果確定、履歴編集、選手管理、大会、バックアップ/復元、全データ削除が正常に動くことを記録する。
5. Supabase Auth のメール確認・招待・パスワードリセットをどの方法で運用するか決める。公開サインアップは原則オフにし、管理者がメンバーを招待する運用を推奨する。

### フェーズ1 — 認証の追加（旧アクセスはまだ止めない）

1. Supabase Auth を有効にし、管理者がテスト用メンバーを1人招待する。
2. **実装済み（このブランチ上）:** フロントエンドにメールアドレス/パスワードのログイン画面、セッション復元、ログアウトを追加した。ログアウト時にはRealtime購読も解除する。まだデプロイ・実ユーザー検証前であり、本番のRLSを変更していない。
3. パスワードを `sessionStorage` や独自管理者オブジェクトに保存しない。
3. AuthユーザーIDと役割を結びつける `profiles` または `user_roles` テーブルを作成する。役割の変更は管理者だけが行えるようにし、ユーザー自身が自分の role を更新できないポリシーにする。
4. 管理者判定はクライアントのフラグではなく、RLSで参照できるDB側の役割情報に基づいて実施する。
5. この段階では既存の匿名アクセスを残し、テストユーザーで全機能を検証する。

### フェーズ2 — 共有データの権限を分離

1. `app_state` の SELECT を `authenticated` のみへ移す。ただし、全メンバーが同じサークルデータを閲覧する設計なら、認証済みメンバー全員に読み取りを許可する。
2. `save_app_state` の EXECUTE を `authenticated` のみに変更し、未認証の `anon` から呼び出せないようにする。
3. RPC内部でも `auth.uid()` が存在することと、ユーザーが有効なメンバーであることを検証する。管理者限定操作は別RPCに分離し、DB側で管理者役割を検証する。
4. `app_state` の Realtime購読が認証済みセッションで動くことを確認する。
5. `anon` 向け権限を削る前に、全メンバーのログイン完了を確認し、移行時刻と切り戻しSQLを準備する。

### フェーズ3 — 管理者操作をDB側で保護

- 管理者アカウント作成・変更・削除、全データ削除、大会情報更新依頼、データ復元を管理者専用RPCに整理する。
- 各RPCは呼び出し元の `auth.uid()` と管理者役割をサーバー側で検証する。
- `admin_accounts` の旧ユーザー名・パスワード認証は、新しい管理者Authアカウントと動作確認が済むまで削除しない。
- 最後の有効管理者を誤って消さない保護と、操作ログを検討する。

### フェーズ4 — 自動バックアップと運用の更新

- RLS適用後、GitHub Actionsが publishable key で非公開の `app_state` を読めなくなるのは正常な結果。ワークフローをそのまま放置しない。
- 推奨は、必要なデータだけをサーバー側の保護された処理でエクスポートする構成。サービスロールキーを GitHub の公開ファイルやブラウザへ置かない。GitHub Actions secret を使う場合も、最小権限と漏えい時のローテーション手順を用意する。
- RLS移行後にバックアップ、復元、Supabaseのkeepaliveを個別にテストし、成功を確認する。
- 既存の暗号化バックアップを使って、隔離した検証環境で復元テストを実施する。

## 受け入れテスト

- 未ログインのブラウザでは共有データを読み取れず、保存RPCも実行できない。
- 招待された有効メンバーはログイン後、共有データを読み取り、許可された練習データを更新できる。
- メンバーは自分の権限を管理者へ昇格できない。
- 管理者だけがメンバー招待、権限変更、全データ削除、管理者設定を行える。
- 2台以上の端末で練習記録を同時編集したとき、既存の競合処理とRealtime同期が動く。
- 練習・結果確定・履歴編集・選手・大会・札分け・AI分析・バックアップ・復元が動く。
- GitHub Actionsのバックアップとkeepaliveが成功し、復元可能である。
- ブラウザのソース・ネットワーク通信・Git履歴に秘密鍵やパスワードが含まれない。

## 切り戻し方針

RLS変更を行う前に、現在のポリシーと関数権限をSQLで記録する。障害時はその記録に基づき、まずアプリの利用を復旧し、その後原因を調査する。権限を広げた状態を恒久対応にせず、期限を決めた復旧に限定する。

## 重要な注意

このリポジトリへの変更だけでは、Supabaseプロジェクトの Auth 設定、DBポリシー、既存データは自動的には変更されない。Supabase SQL Editor と Dashboard での作業、および実ユーザーでのテストが必要。実際の権限変更は、移行用SQLと切り戻し手順をレビューしてから別段階で行う。
