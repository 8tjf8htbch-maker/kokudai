# 國大練習AI：接続方式の検討

## 現状

- フロントエンドは GitHub Pages で配信される静的Webアプリ。
- 戦績データは現在のSupabase共有データからブラウザに読み込まれる。
- Python分析エンジンは `ai_engine/karuta_analysis.py` にあり、現時点では独立したライブラリ。
- ブラウザのJavaScriptからPythonファイルを直接実行することはできない。
- 現在のREAL AIはGeminiを呼び出す既存経路であり、この初期実装とはまだ接続されていない。

## 接続案

### A. 自分で管理するPythonサーバー（本命候補）

1. FastAPIなどでPython分析エンジンを呼び出すAPIを用意する。
2. HTTPSでのみ通信する。
3. 認証済みのアプリ利用者だけがAPIを呼べるようにする。
4. サーバー側でも対象データへのアクセス権限を検証する。
5. リクエスト本文や選手名・試合データをログに出さない。
6. APIの入力サイズ制限、レート制限、依存関係の更新、バックアップ・監視方針を整える。
7. Geminiなどの外部生成AI APIは使用せず、分析は自分のPythonコード内で行う。

**注意：** 自分で管理するサーバーを使っても、ホスティング事業者の基盤を利用する場合は、その事業者を完全に介さないわけではない。サーバーの運用者・保存場所・ログ・バックアップ方針を確認してから実データを送る。

### B. ブラウザ内だけで分析する

既存のJavaScriptで分析処理を実行する方式。データを分析用サーバーに送らずに済むため、データ移動を最小化できる。ただしPythonエンジンをそのまま実行する方式ではなく、分析ロジックをJavaScriptに移植する必要がある。

### C. Pythonをブラウザ内で実行する

Pyodide等を使う方法もあるが、初期ロードが重くなりやすく、依存ファイルの配信・更新管理も必要。外部CDNに依存させると、その配信元への依存が発生するため、採用するなら配信方法を先に設計する。

## 推奨する進め方

- まずはA案のAPI設計だけを行い、ローカルの合成データで動作を検証する。
- その段階ではSupabaseや本番の選手データに接続しない。
- APIの認証・権限確認・ログ抑制の設計レビューが済むまで本番アプリとは接続しない。
- サーバーの管理方法と費用が決まるまではデプロイしない。
- 既存のGemini経路は、比較テストと切替手順が整うまで残す。

## 接続APIの初期契約案

- メソッド：`POST`
- パス：`/api/analysis/v1/analyze`
- 入力：選手の集計、直近の試合結果、全期間の対戦相手集計、大会集計
- 出力：`engine`、`practiceSummary`、`tournamentSummary`、`trend`、`opponents`、`insights`、`suggestions`、`limitations`
- APIは分析結果を永続保存しない。
- 入力データは合成データで試験し、公開リポジトリに実際の選手名や実データをコミットしない。

この文書は設計案であり、サーバーや本番アプリへの接続はまだ実施していない。


## 次段階：既存アプリへの接続設計（2026-10）

### 推奨するデータフロー

1. 利用者がアプリ内で選手を選び、「ローカル分析」を実行する。
2. 認証済み利用者であることをAPI側で検証する。
3. API側で、その利用者が対象選手のデータを参照できるかを検証する。
4. 権限が確認できたデータだけを分析エンジンに渡し、結果を返す。
5. 分析データと結果は保存せず、生成AI APIへ送信しない。

### 接続前に解決が必要なブロッカー

- 現在の画面で使うログイン情報と、API側で検証できるユーザー認証は同じものとは限らない。ブラウザに共通APIトークンを埋め込む方式は採用しない。
- 現在の共有データアクセスは、API側で対象選手への権限を確認できる設計に整理する必要がある。
- Supabase Auth / RLSの導入・整理が必要かを別途判断する。既存の認証・権限変更を含むPRは、レビューなしにマージしない。
- APIサーバーの運用先、HTTPS、ログ保持、アクセス制限、費用を決めるまで公開しない。

### 段階的な接続手順

1. **完了：** Python分析エンジンとHTTP APIを独立したPR上に実装。
2. **完了：** 合成データを使ったAPI起動・認証・入力制限テストをCIで実施。
3. **次：** アプリの既存認証・データ共有方式を確認し、APIが安全に利用者を識別できる方法を決める。
4. **その後：** 開発環境だけでAPI接続を実装し、合成データでUI表示を確認。
5. **最後：** 権限レビューと運用先の確認後に限り、本番接続を検討する。

### 初回UIの想定

- 「REAL AI」とは別に「記録分析（ローカル）」として表示し、外部生成AIを使う機能と混同させない。
- 結果には勝率、直近の推移、相手別の記録、提案、サンプル数の注意を表示する。
- APIに接続できない場合でも既存画面・記録が壊れないようにし、既存REAL AIを自動で切り替えたり削除したりしない。
- ユーザーが明示的に実行した時だけ分析を開始し、選手を変更した際などに自動送信しない。

この接続設計はまだ本番実装ではない。extensions.js とSupabase設定は変更していない。
